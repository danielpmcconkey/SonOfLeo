## What's next

**The Context design is the live decision.** Dan's vision, as sketched in the
uncommitted files:

```fsharp
type Context = { dataContext: DataContext; loggingContext: LoggingContext }
let create transactionNeed auditAction = ...
```

with `TransactionNeed = NoTransaction | NewTransaction | ExistingTransaction of DbTransaction`,
and a route declaring both postures in one line:

```fsharp
let context = Context.create NewTransaction JournalEntryPostNew
let context = Context.create NoTransaction FetchOnly
```

I argued against it and lost, correctly. Three of his points that future-you
should not re-litigate:

- **`FetchOnly` means reads get an audit identity.** That was my main objection
  (reads don't take an envelope); Dan's answer is that access logging is a real
  forensic requirement. It's a position, not a fudge.
- **Audit and diagnostic logging can be co-tenants.** I claimed they "must not
  share a home." Dan has spent a career in banking and says they always ride the
  same rails with different sinks, classification and retention. He's right; I
  withdrew it.
- **`withoutTransaction (fun tran -> ...)` is misleading ceremony** — 24 of them
  in the routes, a lambda impersonating a bracket with nothing to close. Killing
  it is a genuine motivation, not a rationalisation. Note that I offered Dan the
  plain-value alternative back at D1 and didn't push when he took the bracket.

Also in its favour: `ExistingTransaction` is the batch-import seam that #93a /
ARCH-1 have wanted since the audit, and the `// todo: add a user context so Jodi
can use this system too someday` is a concrete third rider.

**The one open objection Dan accepted:** creation and completion are divorced.
`Context.create NewTransaction` opens a transaction; `withAutoCommitTransaction`
closes it; nothing binds them, so a route that forgets the bracket leaks a
connection and silently discards its work while returning `Ok`. `createDbTransaction`
also went public again. Proposed fix, which Dan did not reject:

```fsharp
let withNewTransactionContext (action: AuditableAction) (func: Context -> Result<'T, AppError>) : Result<'T, AppError>
```

Reads keep the plain `Context.create NoTransaction FetchOnly` — nothing to close,
so nothing to seal. The asymmetry is a feature: the call shape tells you whether
there is a lifecycle.

Dan noted, correctly, that `withManualCommitTransaction` already broke the seal —
it was "a public createTransaction with extra steps." The live distinction is
that leaking it required ignoring a DU that put a transaction in your hand, where
leaking `Context.create NewTransaction` requires only *not writing a line*.
