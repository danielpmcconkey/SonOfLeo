## Where we are

**ArchiMate architecture model is the active work.** Dan decided to use
ArchiMate as the authoritative constraint model for SonOfLeo. The model
lives at `Architecture/SonOfLeo.archimate`. A deterministic validation
skill lives at `Skills/ArchiMate/`.

The model has three purposes:
1. **Constraint model** — motivation-layer principles/constraints are
   the source of truth for "what matters." Application-layer elements
   describe the system that must satisfy them.
2. **Cladistic capability taxonomy** — ApplicationFunctions under
   Capabilities define WHAT the system does (behaviour and outcome, not
   implementation). Components under Src realize capabilities. Realization
   fan-out is the diagnostic signal for code smells.
3. **Truthiness hierarchy** — code → ArchiMate → markdown. Periodic drift
   reviews. Code review agents read the model alongside the code.

### Capability definitions written

All existing ApplicationFunctions in the Capabilities folder received
`<documentation>` definitions. Key design decisions made during this:

- **Functions are the "what," not the "how."** Definitions must read the
  same regardless of implementation language.
- **Cladistic taxonomy.** Parent functions define the synapomorphy —
  "everything in this clade is more related to everything else in the
  clade than to any single thing outside it." Realization fan-out is the
  diagnostic.
- **Folders duplicate elements.** Every folder has an identically-named
  ApplicationFunction element — folders are Archi organisation, elements
  are model citizens that participate in relationships.

### New clades created

- **Lifecycle functions** (under Utility) — moved ActivityPeriod functions

  period"). Added "Transition an entity between lifecycle states."
- **Data ingestion functions** (under Financial services) — staged entry
  vocabulary, ingestion source, status transitions, deduplication.
- **Journal entry functions** (under Ledger functions).
- **"Record actor"** added to Observability functions — the "who did it"

### Cross-domain dependency analysis

Dan reordered `Model.fsproj` to isolate domains. DataIngestion is now a
clean block. The remaining interleave is between CashFlow and
Classification, caused by two type definitions:

- **TransactionPointer** (CashFlowComponent) — uses `StageEntryLineId`
- **ClassificationClaimant** (ClassificationComponent) — uses
  `PaymentAgreementId`

Dan's position: this is a sign something escaped its intended scope. The
ArchiMate model is being built partly to make this visible and find the
fix. F#'s compile-order constraint is a design philosophy, not a
limitation — putting everything in one project circumvents it.

### Design decision: lifecycle capability split

Discussed the relationship between "Transition an entity between
lifecycle states" (generic, Lifecycle clade) and "Transition stage entry
status" (domain, DataIngestion). Dan's ruling:

- **StageEntryStatusTransition** realizes the generic lifecycle capability
  — it IS the lifecycle engine (state machine, validation).
- **StageEntryHeader** realizes the domain-specific capability — it
  orchestrates the full operation (fetch current, validate, record).
- Same split as DAL vs entity. Infrastructure vs operation.
