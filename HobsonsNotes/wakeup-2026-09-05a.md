## What happened this session

### Namespace refactor + ActivityPeriod extraction

`AccountActivityPeriod` extracted to a shared `Model.ActivityPeriod`
type, reused by both Account and MasterAgreement. Namespace flattening
across all Ledger modules (`Model.Ledger.Accounts` → `Model.Ledger.Account`,
etc.). JournalEntry/StageEntry `lines` disambiguated to `jeLines`/`seLines`.

### ActivityPeriod.isActive vs isAvailable

Dan split the concept: `isActive` is strict (start date gates — for the
sweep), `isAvailable` is lenient (respects `BeginValidationBehavior` —
for creation/validation). Accounts use `NotConsideredAvailableBeforeBeginDate`,
MasterAgreements use `ConsideredAvailableBeforeBeginDate`. Future-start
agreements can be created but won't be swept until they start.

### InstanceOrchestration replaces InvoiceOrchestration

`InvoiceOrchestration.fs` renamed to `InstanceOrchestration.fs`. New
`InstanceComposite` type wraps Instance + InvoiceComposite list. The
Instance is always present; invoices may be empty (variable obligation,
bill not in hand). This is the tree that was already nested inside
`Agreement` — promoted to a first-class composite. The §9 gauntlet
stays at the InvoiceComposite level; InstanceComposite is the front door.

### Cadence redesign — nextInstance pointer

`firstInstance` on MasterAgreement was explored and rejected (LLM
can't be trusted to derive it; storing it introduces validation
complexity on cadence changes). Replaced by: the Cadence type itself
carries a `nextInstance` date that advances every sweep. Cadence is now
a private record `{ cadenceType: CadenceType; nextInstance: CadenceNextInstance }`
in `Src/Utilities/Cadence.fs`. Validation ensures nextInstance is a
valid occurrence of the cadence type. On cadence change, the new type
+ new nextInstance are validated together — they can't drift.

Cadence type constraints tightened: `DateInMonthNumber` capped at 1–28
(was 1–31), `WeekInMonthNumber` capped at 1–4 (was 1–5). Use `Last`
for end-of-month semantics. REQ-CF-7.5 (clamping) withdrawn — the type
system prevents the scenario.

### Sweep creates Instances only — no Invoices

`ProjectionSweep` no longer creates Invoices for fixed-amount PAs.
Invoices are created downstream: by the invoice parsing script (when
a bill PDF is parsed) or by the operator. The Projection route derives
expected amounts from `PA.expectedAmount` for fixed obligations and
surfaces "amount TBD" for variable obligations without invoices. This
eliminated the due-date-guessing problem.

### Derived lifecycle states

`paymentState` and `postedState` on Invoice are now derived, not
operator-set. Creating a Payment auto-derives paymentState from the
sum of payments vs invoice amount. `TransitionPaymentsToPosted`
auto-derives postedState from Payment pointer states. The operator
sets only `invoiceState` (bill arrived/sent) and `blocker` (why
something is stuck). This is a conceptual decision — the spec hasn't
been updated yet to formalize it.

### Saturday state machine

The Saturday routine is now designed as a deterministic state machine
(inspired by the EtlReverseEngineering engine). The full flow — from
ingestion through reports — runs as one machine. Mechanical nodes run
scripts/CLI routes. Judgment nodes invoke `claude -p` with blueprint
prompts. Failure routes to a global handler.

Draft: `HobsonsNotes/saturday-state-machine-draft-2026-09-04.md`

Key design decisions in the state machine:
- Classification is split into two passes (or potentially one after
  reordering): account classification and obligation classification
- Shadow post → shadow recon loop catches mismatches before real posting
- `ProcessObligations` matches invoices to stage entries by PA account
  pattern + amount + date window (not by external invoice ID — the FI
  feed doesn't carry the counterparty's invoice number)
- The matching date window is `invoiceDate` → `dueDate + 5 days`

### Classification redesign — ClassificationClaimant

The classifier now supports two claimant types: `Account` (existing —
classify the line to a ledger account) and `PaymentAgreement` (new —
tag the stage entry as belonging to an obligation). This allows
description-based rules to link stage entries to obligations (e.g.,
"CITY OF CONCORD" → PA for W&E).

Open question: one pass or two? Two passes (account in ingestion,
obligation after invoice creation) is simpler but risks inconsistency
between the account the classifier assigned and the account the PA
defines. One pass (classification moves after invoice creation, handles
both) is cleaner but requires reordering the ingest pipeline. Dan is
thinking on this.

## Post-session addendum (2026-09-06)

After the 2026-09-05 Saturday routine in LeoBloom (which went poorly —
direction bugs, wrong-month tenant invoices, obligation instances
confirmed with wrong amounts, multiple void-and-reposts), Dan and Hobson
reviewed the state machine draft and revised it based on what actually
broke. The revised draft is in place at
`HobsonsNotes/saturday-state-machine-draft-2026-09-04.md`.

**Decisions made:**

1. **Two-pass classification is confirmed.** Account rules first
   (2.2.2.0), PA rules second (2.2.5.0). Separate passes, separate rule
   sets, no priority conflicts. Dan's rationale: he doesn't want to
   deconflict when a stage entry matches both an account rule and a PA
   rule in the same pass.

2. **Sweep now creates invoices for fixed-amount PAs.** Reverses the
   "sweep creates instances only" decision from this session. For PAs
   with a known fixed amount (car payment, mortgage, phone bill), the
   sweep creates both an Instance and an Invoice (amount from the PA, due
   date = invoice date + `daysDueAfterInvoice`). Variable-amount PAs
   (utilities) get Instances only. If an actual bill arrives, the parsing
   step overwrites the sweep-generated Invoice's amount and due date.

3. **`daysDueAfterInvoice` on PaymentAgreement.** New integer field. 0 =
   due on the cadence date ("due on arrival"). Enables the sweep to
   compute due dates without an external bill. Not yet in the schema.

4. **Shadow recon validates indelible data only.** JEs are indelible
   (void is the only correction). Obligation linkage is mutable
   (correctable in place). Shadow post + recon loop (Phase 4) validates
   JE legs. Obligation matching is validated by the operator reviewing
   ProcessObligations output, but doesn't need shadow/rollback
   protection. No separate "shadow cash flow report" — the trial balance
   shadow is sufficient.

5. **No ops layer.** Dan considered and rejected an orchestration layer
   between InterfaceBridge and ModelOrchestrator. The Saturday routine is
   orchestrated by the state machine (external), not by a CLI route.

6. **Tenant invoices bill in arrears.** The billing period is derived
   from the agreement's cadence, not from the calendar. Step 7.0.0.0
   explicitly says "prior month." This is deterministic — the LLM does
   not choose which month to bill.

**Standing corrections updated:**
- "Sweep creates Instances only" → now creates Invoices for fixed-amount
  PAs too.
- "Classification one-pass vs two-pass decision" → decided: two passes.
