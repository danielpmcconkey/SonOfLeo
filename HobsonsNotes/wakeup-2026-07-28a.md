## What happened last session

**1. The Context design landed, and the shape is Dan's, not mine.** How a route
declares its transaction posture:

```fsharp
// writes — creates a transaction, commits on Ok, rolls back on Error
runRouteAndAutoCompleteTransaction JournalEntryPostNew (fun context -> result { ... })

// reads — a plain value with nothing to close
let context = Context.create NoTransaction FetchOnly
```

`runRouteAndAutoCompleteTransaction` lives in `Src/InterfaceBridge/CommandRoute.fs`
(Dan moved it there from a short-lived `AutoCommitPipeline.fs`, now deleted).
The DAL primitive it calls was renamed `withAutoCommitTransaction` →
`runWithAutoCompleteTransaction`. `withoutTransaction` is gone from `Src`
entirely — the 24 lambdas impersonating brackets are dead. Current census: 2
routes take a transaction (JournalEntry PostNew and Void), 15 take a
transactionless context, none hand-roll `NewTransaction`.

**2. I spent a long time pushing a "seal" Dan never asked for, and I was wrong
three times running.** Read this before you reach for it again:

- I proposed making the `Context` record private so only sanctioned doors could
  build one. That forces the bracket into the Context project.
- Dan's objection, which is correct: **Context is a container.** Its behaviour
  should be getting and setting with respect to the container, nothing more.
  Transaction lifecycle is not Context's job.
- My fallback — declaring posture in the route table and executing the lifecycle
  in `Program.fs` — was worse. It would have made *only* CLI-route-level tests
  able to roll back, killing unit and orchestrator testing, and bought nothing
  but a bigger route table.
- **Dan is not seeking a compile-time guarantee here.** Create, then commit or
  roll back in a `finally`, is as old as app-layer/persistence interaction and he
  is content with it. A route author can still hand-roll `create NewTransaction`
  and leak a connection. That is a code-review catch. He knows. Leave it.

**3. Test-side plumbing, and a real discovery.** `Rollback.fs` is deleted and
replaced by `Tests/Tests.Integrated/Railroad.fs`:

```fsharp
let railroadWrapper (railroad: Result<'T, AppError>) : unit =
    match railroad with
    | Ok _ -> ()
    | Error e -> Assert.Fail(AppError.toMessage e)
```

Dan asked whether the railroad-ending match was now vestigial. **It is not, and
this was worth proving.** I built a throwaway xUnit project in the scratchpad and
ran it: a `[<Fact>]` returning `Result<unit, AppError>` is silently discarded by
xUnit 2.9.3. The test passes green while the assertions inside the railway never
ran. `Failed: 1, Passed: 2` — the only failure was the control.

The subtlety that nearly hid this: an *unconstrained* computation expression makes
the test method generic, and xUnit rejects generic facts loudly with
`[Fact] methods are not allowed to be generic`. That looks like protection. It
isn't — it evaporates the moment the test calls something returning
`Result<_, AppError>`, which is every real test. `let` instead of `let!` leaves
the error type unpinned and produces the same misleading error.

`railroadWrapper` goes **last and once**, at the outermost expression — outside
`runFuncAndAutoRollback`, not inside it, so it also catches rollback failures.
Both it and the bracket are generic in `'T`, so no `match ... | Ok _ -> Ok ()`
conversion is needed to feed them.

`runFuncAndAutoRollback` (in `Tests/Tests.Integrated/InterfaceBridge/_routeResolver.fs`)
is the test-side mirror: create a context, run, always roll back. **Known
limitation: it does not roll back route tests**, because write routes create and
commit their own transaction internally. Route tests remain on the capture-the-ID
cleanup form. Dan called that unacceptable in principle — 80% of why he built
transactions was to stop tracking created entities in tests — so this will come
back. Fixing it means routes accepting a context from outside, which is what
`ExistingTransaction` exists for. Not yet designed.
