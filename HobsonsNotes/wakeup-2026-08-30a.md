## What happened this session

Hobson proposed the CashFlow CLI routes needed to make Saturday
deterministic. Key outcome: split the world into [DET] routes the CLI

**CashFlowOps routes (Saturday operations):**

**Key design decisions from the conversation:**
- CreatePayment, CreateInvoice, UpdateInvoice go straight to Model CRUD
  from their routes — no CashFlowOps wrapper. Orchestrator provides
  validation (`confirmInvoiceComposite`, `confirmPayment`).
- `ObligationStatus` is not a separate function — it's `fetchFiltered`
  with a specific filter. The route picks the filter, formats the output.
- `GenerateTenantInvoices` dropped — belongs in LeoBloomOps, not SonOfLeo.
  Tenant details are currently hard-wired; needs future design.
- Every mutating route must return the complete state of what it touched
  so Hobson never needs a follow-up query for the summary.

### Invoice lifecycle constraints (§9)

Seven constraints validated by `confirmInvoiceComposite` after any
Invoice create or update (persist, fetch composite, validate, rollback):

1. FullyPaid requires sum(payments) = invoice amount
2. PostedToLedger requires FullyPaid
3. FullyPaid requires Blocker = None
4. Blocker can't be set while FullyPaid
5. PartiallyPaid requires at least one Payment
6. PostedToLedger requires all Payments have JE pointers
7. PartiallyPosted requires at least one Payment with JE pointer

These are NOT a state machine — any valid value can be set directly.
The constraints are cross-entity composite checks, not transition rules.
