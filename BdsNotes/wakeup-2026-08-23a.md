### Decisions worth keeping

**REQ-STG-10.4 sorting is asserted on key sequences, not entity order.** The `order by`
clauses carry no tiebreaker and the staged data ties on all four keys. Entity order is not the
query's promise. Key sequences are also collation-independent — whatever the database calls
ascending, descending must be its reverse. A separate entry-date test asserts real sortedness,
because dates are the one key whose ordering does not require agreeing with Postgres about
collation.

**The line type filter is tested paired with an amount.** Double entry puts a Debit and a
Credit on every staged entry, so a line-type filter alone returns the whole table whatever
value it gets — it would pass just as green if the implementation dropped the field. Paired
with an amount carried by one leg it becomes falsifiable. Confirmed: nulling the `lineType`
clause reddens only that test.

## The open question — REQ-STG-2.24

Read the requirement in `Specs/Behavioral/DataIngestion.md` (§2, just after REQ-STG-2.7).
It says the `status` column on a staged entry must **always** reflect the `to_status` of the
most recent audit record; the trail is the source of truth, the column is a denormalization,
and divergence is a defect.

Hobson wrote it from a finding BD raised. Dan's objection to Hobson, verbatim: **"'Always' is
not verifiable."** He is right, and it constrains the test, not just the spec.

### Why a test cannot cover it

The column is written at four moments — initial insert during ingestion, classification
setting Classified/NoMatch/Conflict, operator update, and posting. All four currently route
through `updateHeaderStatusAndAddAuditRecord` (`Src/ModelOrchestrator/StageEntryOrchestration.fs:287`,
private), which writes the column and the audit row as a pair. Asserting the invariant at
those four points is honest but is "at these four moments in today's code," not "always." A
fifth caller added later sails past every one of them.

The gap is structural. `StageEntryHeader.updateStatus`
(`Src/Model/DataIngestion/StageEntryHeader.fs:326`) writes the column alone and is public;
the only guard is the doc comment above it. The generic field-update path has the same hole,
marked `statusUpdate // note: you still need to add an entry to the audit table`
(same file, ~line 290). Two write paths to a denormalized column, guarded by comments.

### The proposal Dan has not ruled on

Dan's first response was that he cannot make `updateStatus` private, because the orchestrator
that pairs the two writes lives in a different binary. True of the orchestrator — but
`StageEntryStatusTransition.fs` and `StageEntryHeader.fs` are **both in `Model.fsproj`**
(lines 21 and 25, transition compiling first). Both tables are already in the same assembly.

So move the pairing down rather than the privacy up: make `updateStatus` private inside
`StageEntryHeader`, and expose one function taking the already-validated transition —

```fsharp
let updateStatusWithAuditRecord context (transition: StageEntryStatusTransition) =
    result {
        let! updated =
            transition
            |> StageEntryStatusTransition.stageEntryHeaderId
            |> updateStatus context (transition |> StageEntryStatusTransition.toStatus)
        do! transition |> StageEntryStatusTransition.insertNewToDb context
        return updated
    }
```

The orchestrator keeps what is genuinely its job — fetching the prior transition, computing
`fromStatus`, `confirmValidTransition` — and loses only the ability to write the column alone.

The point that matters more than the pairing: **the column's value comes off the transition.**
One value, one source. They cannot disagree, rather than being discouraged from disagreeing.

Two loose ends named at the time, unresolved:

- `StageEntryHeaderFieldUpdates` still carries a `statusUpdate` field — the second door.
  Dropping it also deletes the redundant first write that
  `StageEntryOrchestration.fs:513` already apologizes for in a comment.
- Ingestion's bulk insert writes headers and transitions as two batched passes
  (`StageEntryOrchestration.fs:418-427`). The invariant holds by construction there, but it
  is structurally a third door.

Fallback if Dan does not want the Src change: a `Checks/check-stage-status-write.sh` in the
style of `check-clock` / `check-npgsql`. Weaker than the compiler, same shape of guard the
repo already uses for other "always" rules.

**BD's part either way:** fix `StageEntryIngestion.fs:493` (below) and write the checkpoint
tests. The Src change is Dan's or the pipeline's.
