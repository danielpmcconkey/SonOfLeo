## Known-weak — do not trust these

- **`check-traceability`'s PASS means nothing off `main`.** `Checks/check-traceability.sh:8`
  exits 0 unless the branch is `main`, so every green `run-all.sh` on a feature branch includes
  a no-op. Run `Skills/SonOfLeoRequirementsAudit/traceability-audit.sh .` directly to get a real
  answer. This session found a live merge blocker that way (REQ-STG-5.9, untested and unwaived,
  green on the branch and red on merge).
- **The pre-commit hook is weaker still.** It runs `run-all.sh --quick`, which skips
  `check-traceability` as slow — 7 passed, 2 skipped. Run the full check by hand before
  presenting.
- **A mutation that is not asymmetric proves nothing.** BD perturbed a helper that both sides
  of an `Assert.Equal` ran through; expected and actual moved together and the test stayed
  green. Caught only because the "failure" was a pass. See
  `CompoundedLearnings/articles/testing/mutation-proves-liveness-not-aim.md` — the article
  covers the sibling case (mutation proves liveness, not aim) and this belongs with it.
- **Item 9's fix is structurally right and currently unobservable.** The four
  `fetchByReference` tests now count distinct entries rather than reference rows, but the
  fixture gives each entry at most one reference per institution-and-text pair, so the two
  quantities are equal today. No mutation can show the difference — only that the assertion
  runs.
- **`Assert.` is not the only assertion here.** Sad-path tests assert through `isCorrectError` /
  `isCorrectErrorString` in `Tests/Tests.Helpers/SadPath.fs`. A sweep grepping for `Assert.`
  will call them empty. They are not.
- **A stale test name is invisible to every check.** Fifteen names claimed account codes after

## Why REQ-STG-5.4 stayed broken through a full mutation pass

Worth reading before trusting your own evidence next time.

Audit finding BC-STG-1 said the REQ-STG-5.4 test exercised `ManyMatchesClearWinner` rather than
`OneMatch`. BD renamed that test in `428ea4d`, strengthened its body, mutated every assertion,
watched each go red — and left it pointed at a line two rules match. The requirement is about
*exactly one* rule matching. It was cited, counted as covered by the traceability grep, and
never exercised. The sharpened name made it worse: a vague false claim reads as vague, a
precise false claim reads as verified.

The trap generalises: **mutation evidence answers "is this assertion live", never "is this test
aimed at the scenario its name claims".** The fix, in `dd2bfc8`, was to match on the outcome DU
case itself so the scenario is pinned rather than assumed.
