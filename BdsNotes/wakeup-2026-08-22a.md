### The three step-8 findings, and how they landed

Read `BdsNotes/batch-b-draft-names.md` for the full write-up. In brief:

**`REQ-CR-4.8` was false when it was waived.** `createNewClassificationRule` took `isActive` as an
argument, so the mechanism the requirement said must not exist was the fifth parameter. It also
made approved name #5 unwritable — the test would have asserted that the `true` it passed came
back as `true`. Dan removed the parameter.

**The `codeAtMatch` filter never worked.** It bound `@cr.code_at_match`, the only dotted parameter
name in `Src/`; Npgsql stops parsing a placeholder at the dot. The vector had no test, which is
how it survived. Predicted the test would go red; it went green after the fix.

**`REQ-CR-1.21`'s waiver was right for the wrong reason.** `ClassificationRule.reconstitute` builds
the rule body with `fromJson`, which materialises `Money` by reflection. `Money.create` never runs
on the read path. See Known-weak.

### Mutation evidence

Every assertion in the batch perturbed, run, failure read, reverted. The technique that made 60-odd
assertions tractable: a script that perturbs the **k-th assertion in every test**, one pass per
position, because a test stops at its first failure. Seven positional passes plus bespoke mutations
for assertions whose expected side is computed rather than literal. The seven sad-path tests carry
no `Assert.` at all — they were proven separately by swapping the expected error DU case, and all
11 cases came back naming the real error.

Restore between passes used `cp` then `touch`, never `mv` and never git — the branch-switching and
restore families are guarded, and `mv` preserves mtime so MSBuild skips the rebuild and hands you a
green run of stale code.

## Two ways BD got it wrong, both caught by the checks and not by BD

Worth reading before you trust your own process on the next batch.

**Two approved names were never written.** `REQ-CR-5.4`'s pair — the sort tests. The read block got
written, the update block got written, and nothing noticed the gap between them.
`check-traceability` found it. **Diff the tests you wrote against the approved name list before you
call a batch done**; nothing in the loop does that for you.

**BD created a stale waiver two turns after warning Dan about that exact trap.** A comment in
`Tests/Tests.Helpers/TestDataStage.fs` explained the inactive archetype by naming `REQ-CR-4.8`. The
audit greps whole files under `Tests/` and cannot parse F#, so prose counts as a citation: the waived
clause reported as covered, and the stale-waiver invariant fired. The rule is not about test names,
it is about **any occurrence of the ID pattern in any file under `Tests/`**. Name requirements in
prose instead.

Both would have committed and pushed clean: the pre-commit hook runs `run-all.sh --quick`, which
skips `check-traceability` as slow. **Run the full `Checks/run-all.sh` before presenting.** That habit
is the only reason either was caught.
