**Critical production bug discovered: nested reader commands in `mapRowForDbRead`.**

`JournalEntryHeader.mapRowForDbRead` calls `validateThenConstruct` → `EntryDate.create(transaction)` → `FiscalPeriod.fetchIdByKey(transaction)`. This secondary DB lookup executes while the outer DataReader is still open on the same connection. Npgsql (PostgreSQL in general) does not support multiple active commands per connection → "A command is already in progress."

This breaks ANY code path that reads a JournalEntryHeader from the DB within a transaction:
- `JournalEntryExternalReference.constructNewAndSaveToDb` → `validateJournalEntryHeader` → `fetchById` → boom
- `JournalEntryComment.constructNewAndSaveToDb` → same path
- `JournalEntryFetching.fetchById` → same path
- `voidJournalEntryOrchestration` → `validateFiscalPeriodIsOpen` → `fetchById` → same path
- `JournalEntryLine.mapRowForDbRead` → `validateAccount` → `Account.fetchById` → same pattern

Same pattern exists wherever `mapRowForDbRead` does secondary lookups. `Account.mapRowForDbRead` is safe (no sub-lookups). `FiscalPeriod.mapRowForDbRead` is safe.

**JournalEntryCreation tests partially implemented** (23 stubs filled in). 17 pass, 6 fail due to the Npgsql bug (all tests involving ext refs, comments, or post-creation fetches).

**Design discussion in progress** for the fix: refactor `executeReaderQuery` to separate row extraction (inside reader loop) from domain object construction (after reader disposal). The reader loop extracts raw values into tuples; construction/validation runs after the reader and command are disposed, when the connection is free for secondary lookups. Dan proposed enforcing this pattern at the DAL level — `executeReaderQuery` takes both a row extractor function and an optional constructor function, does the two-phase internally.
