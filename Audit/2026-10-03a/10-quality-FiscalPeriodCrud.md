# spec-quality-FiscalPeriodCrud

## FP-ATOM-1 — enforcement-gap
- **Location:** Src/Ui.InterfaceBridge/Routes/FiscalPeriodRoutes.fs:26-35 (ensure); Src/Business.CrossDomainOrchestration/FiscalPeriodCreation.fs:34-63; REQ-FP-2.7 vs REQ-SYS-8.1
- **Summary:** The FiscalPeriod Ensure route (REQ-FP-2.7) makes one insert per missing month but runs under NoTransaction, so each insert commits on its own. That breaks REQ-SYS-8.1's all-or-nothing rule for multi-write operations.
- **Resolution:** fix-code

REQ-FP-2.7 creates a fiscal period for every missing month in a range, so one call can make several writes. REQ-SYS-8.1 says: "An operation that makes more than one write performs them in a single database transaction that commits only when the whole operation succeeds and rolls back otherwise." FiscalPeriodRoutes.ensure builds its context with `Context.create NoTransaction FiscalPeriodEnsure`. The Operator CLI then calls the handler directly (Ui.OperatorCli/Program.fs:18: `command.handler payload rest`). With no transaction, App.DataAccessLayer/ExecuteNonQuery.fs (the `dbTransaction |> isNone` branch) opens a fresh connection for every insert, so each insert autocommits. ensureFiscalPeriods maps constructNewAndPersist over the missing keys. If the third of four inserts fails (for example, a unique-key violation because another process created that month in the meantime, or a dropped connection), the first two stay committed while the caller gets an error. That is the half-applied state SYS-8.1 forbids. Other multi-write routes wrap their work in runCommandRouteAndAutoCompleteTransaction: JournalEntryPostNew, IngestRawEntries, every CashFlow create, CashFlowCreateUpcomingInstances. Ensure is a multi-write route that does not. The tests miss this. The REQ-FP-2.7 CDO tests (Tests.Integrated/CrossDomainOrchestration/FiscalPeriodCreation.fs:64-128) run inside runCommandRouteAndAutoRollback, which supplies a transaction the production route never uses. The route test (Tests.Integrated/InterfaceBridge/FiscalPeriodRoutes.fs:229) only checks the happy path. The REQ-SYS-8.1 tests (OperationInstantAndAtomicity.fs:248, 316) cover only JE posting and batch post.

**Action:** Change FiscalPeriodRoutes.ensure to run through runCommandRouteAndAutoCompleteTransaction FiscalPeriodEnsure, like the other multi-write routes. Then add a REQ-SYS-8.1 case for ensure: a range where a later month's insert fails leaves none of the earlier months in the database.

**Why:** FP-2.7 exists for the unattended Saturday run, which calls Ensure every week without checking first. A partial failure there commits some months and not others while reporting an error. Every test passes because the tests give ensure a transaction that the production route lacks, so neither the code nor the tests surface it.

## FP-RECON-1 — enforcement-gap
- **Location:** Src/Business.FinancialServices.Ledger/FiscalPeriod.fs:76-85; Src/Business.FinancialServices.Ledger/FiscalPeriodComponent.fs:26; REQ-FP-1.2, REQ-FP-1.4, REQ-FP-1.5 vs REQ-SYS-2.1
- **Summary:** Reading a fiscal period from the database does not check FP's own data-state rules. The key skips the YYYY-MM check, and start/end dates are not checked against the key, which REQ-SYS-2.1 requires on every read from persistence.
- **Resolution:** fix-code

REQ-SYS-2.1: "Every operation that constructs, persists, or reconstitutes an entity — create, update, and read-from-persistence alike — must enforce that entity's legal data-state rules ... No operation may produce, persist, or return an entity in an illegal data state." On read, FiscalPeriod.reconstitute (FiscalPeriod.fs:76-85) always returns Ok. It builds the key with `FiscalPeriodKey.reconstitute`, an internal back door (`raw |> FiscalPeriodKey`) that skips the REQ-FP-1.2 regex `^\d{4}-(0[1-9]|1[0-2])$` applied by `fromString`. It also copies start_date and end_date straight from the row without checking that they are the first and last day of the keyed month (REQ-FP-1.4 and 1.5). The schema does not cover these rules either. In DbMigration/Scripts/202609071105-CreateLedgerTables.sql:37-48, period_key is `varchar(7) NOT NULL` with a UNIQUE constraint, but there is no CHECK on its format and no CHECK linking start_date and end_date to the key. The runtime role sonofleo_{ENV} has UPDATE on the table, so the database itself does not prevent such a row. In contrast, Account.reconstitute (Account.fs:66-90) re-runs AccountCode.create, AccountName.create, AccountType.fromString and ActivityPeriod.create on read, which is the SYS-2.1 pattern. FiscalPeriod is the ledger entity that does not do this. It matters downstream: REQ-JE-2.5 finds the period by building a key from the entry date, and REQ-JE-1.11 relies on the entry date falling within that period's start and end. A row whose dates do not match its key would be returned as a valid FiscalPeriod and quietly break JE-1.11. The FP-1.x tests (Tests.Integrated/CrossDomainOrchestration/FiscalPeriodCreation.fs:30, Model/Ledger/FiscalPeriod.fs) test the create path only.

**Action:** Make FiscalPeriod.reconstitute validate: build the key with FiscalPeriodKey.fromString instead of the internal reconstitute, and return a typed error when start_date or end_date differs from the dates derived from the key. Alternatively, put the guarantee in the schema with a CHECK on period_key format and a CHECK that start_date/end_date match the key, if Dan prefers that layer. Either way, add a test citing REQ-FP-1.2/1.4/1.5 for the read path.

**Why:** REQ-SYS-2.1 makes read-from-persistence one of the places data-state rules must be enforced, so an invalid row should be refused when it is read rather than spread into later work. Here neither the F# type nor the schema enforces FP-1.2/1.4/1.5 on read, and other ledger entities (Account) do. The JE period invariants (JE-1.11, JE-2.5) depend on these rules holding for every period the system returns, not only for newly created ones.
