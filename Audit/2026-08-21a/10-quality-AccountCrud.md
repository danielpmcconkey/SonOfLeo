# AccountCrud Auditor

_No findings._

## Reasoning

Performed a systematic review of Specs/Behavioral/AccountCrud.md against all seven audit checks. Here is what was examined and why nothing rose to finding level.

1. TERMS VS DEFINITIONS.MD: All terms used consistently. "Calendar Date" (REQ-AC-1.42, 1.43, 1.46, 1.48, 1.48.1, 1.50, 2.7, 2.17, 2.18, 4.1, 4.2, 4.6) matches Definitions.md's "Date (calendar)" definition. "Entity" is used implicitly and correctly — Account is an entity per the Entity definition (user actions insert/update rows, and the table's contents cannot be regenerated from spec alone). No Money/Price/Quantity/Rate terms appear, which is correct since Account CRUD does not handle amounts directly.

2. INTERNAL CONTRADICTIONS: None found. REQ-AC-1.48 (sufficient condition for "not active" via active_end) and REQ-AC-1.50 (complete definition of "active") are complementary, not conflicting — verified by checking all four cases (null active_end, active_end < reference, active_end >= reference, future active_begin). The deactivation guards (4.2-4.6) are mutually independent and consistent. The immutable fields list in 4.22 (ID, code, account type, subtype, active_begin, created_at, parent_id) correctly excludes mutable fields (name per 4.8, external_reference per 4.9, active_end per 4.1) and system-managed fields (modified_at per REQ-SYS-3.3). The type-subtype pairing rules (1.28-1.36) are exhaustive and consistent with the enumerated subtypes in 1.18 — all 9 subtypes are mapped to exactly one type, and all 5 types have their allowed subtypes specified.

3. CONTRADICTIONS WITH SYSTEMWIDE.MD: None. The intro paragraph correctly states cross-cutting policies live in SystemWide.md. The withdrawn table correctly cites REQ-SYS-1.1 (superseding AC-2.1/4.17), REQ-SYS-2.1 (superseding AC-2.19/3.1/4.18/4.21), REQ-SYS-3.2 (superseding AC-1.25/1.26/2.11/2.12), REQ-SYS-3.3 (superseding AC-1.27/4.7), and REQ-SYS-5.1 (superseding AC-2.15) — all verified to exist in SystemWide.md. The AuditEnvelope wording difference between mutation operations (1.48.1, 2.7, 4.3: "Eastern calendar date of the AuditEnvelope's system instant") and read operations (3.9: "US Eastern Time interpretation of the calendar date associated to the system run time") is intentional per resolved finding IE-AC-1 — reads use Calendar.today() by design, not AuditEnvelope.

4. AMBIGUITY: No requirements where two competent developers would diverge. Considered whether length constraints (1.3, 1.8, 1.20) were ambiguous about pre-trim vs post-trim measurement — REQ-SYS-1.1 mandates trimming "before validation," so post-trim is the only reasonable reading. REQ-AC-2.14's "if the calling system specifies that the record should be saved to the DB" implies a persist/no-persist flag — obvious to a competent developer. All reference points for activity status checks are explicitly specified per REQ-AC-1.48.1's policy.

5. INSUFFICIENT ELABORATION: No requirements where WHAT is clear but not enough to implement. Update operations (4.8, 4.9) rely on REQ-SYS-2.1 for data-state enforcement during updates, which is sufficient — the section 1 constraints they must satisfy (e.g., 1.7/1.8 for name, 1.20/1.41/1.49 for external reference) are all concrete and testable.

6. WITHDRAWN TABLE: All 35 withdrawal reasons are sound with no uncovered gaps. Verified each category: DB-ID requirements (1.11-1.15) correctly withdrawn when AccountType moved from DB lookup to DU. Active-flag requirements (1.24, 2.5) correctly superseded by active_begin/active_end dates. Audit-timestamp requirements (1.25-1.27, 2.11-2.12, 4.7) correctly superseded by REQ-SYS-3.2/3.3. Individual immutability requirements (4.10-4.16) correctly consolidated into REQ-AC-4.22. REQ-AC-1.38 (active-parent invariant) correctly superseded by create-time check (2.7) and deactivation child check (4.3). The REQ-AC-1.19.1 withdrawal includes a completed action item ("rename tests to cite 1.19") — verified via grep that all tests now cite REQ-AC-1.19, not 1.19.1. Cross-reference: REQ-DAL-3.4 (cited in AC-2.2 withdrawal) verified to exist in DataAccessLayer.md.

7. THREE-STATE RULE: 77 active requirements = 51 tested + 20 waived + 6 unenforceable. Arithmetic confirmed. Spot-checked test existence for REQ-AC-2.13, 2.21, 3.10 — all have citing tests in Tests.Integrated/. Waiver soundness verified: checked AccountCode.create signature (takes string, smart constructor with Trim/validation), AccountId type (Guid value type), AccountType (discriminated union), Parent ID (Option type), ActiveBegin (NodaTime LocalDate value type). All claims about type-system enforcement hold against the actual F# code in AccountComponent.fs. Unenforceable reasons are sound: 1.48.1 is a policy for spec writers, 2.17 explicitly assigns responsibility to the caller with no validation, and 2.6.1/2.7.1/3.3.1/3.5.2 are contextual annotations about caller scope.
