# reporting-efficacy-auditor

_No findings._

## Reasoning

Examined all 12 tested REQ-RPT requirements across three test files (TrialBalance.fs, AccountBalance.fs, ReportRoutes.fs), plus the source implementations (TrialBalance.fs, AccountBalance.fs), the fixture setup (TestDataStage.fs), and the test helper (EntityFunctions.fs). Checked each against all four audit criteria: behavioral coverage, assertion quality, negative coverage, and uncited behavior.

BEHAVIORAL COVERAGE: Every tested REQ has a test that exercises the described behavior. RPT-1.2 checks account count, inactive account presence, and zero-activity values. RPT-1.4 derives leaf-account expected values from fixture journal entry lines using list operations (sumLinesForAccount helper at class scope). RPT-1.5 recursively finds all descendants in fixture data and sums their lines -- verified that entertainment5650 (which has both voided and unvoided entries) is a descendant of expenses5000, so the parent roll-up implicitly exercises voided-entry exclusion. RPT-1.6 builds a depth-first walk from fixture accounts and asserts exact list equality, with a sort-discriminator account (F-5305, parentless, coded to sort between F-5300 and F-5310 alphabetically) that prevents a flat sort from passing. RPT-1.7 checks four levels of nesting. RPT-1.8 uses accounts that confirmed have both voided (75.00) and unvoided (86.04) entries in the fixture (entertainment5650 and creditCard2220). RPT-1.9 uses temporal entries at today-3, today-1, and today with cutoff at today-2, so the filter genuinely excludes 2 of 3 entries. RPT-1.10 tests both debit-normal (expense) and credit-normal (liability) accounts with correct expected formulas. RPT-1.11 checks zero values for a no-activity account. RPT-2.2 tests data-only mode end-to-end with count and value assertions. RPT-2.3 tests file creation and path return in report mode. RPT-2.4 tests date interpolation with a derived expected date string.

ASSERTION QUALITY: All TrialBalance and AccountBalance tests use exact-equality assertions on expected values derived from fixture data via list operations, not from system functions in the call chain. Verified that sumLinesForAccount (TrialBalance.fs) operates on fixture.Data.journalEntries filtered by voidedAt using accessor functions only. Verified that sumJournalEntryLinesByAccountIdAndType (AccountBalance.fs) when called with unvoidedOnly=true uses JournalEntryHeader.fetchById which is NOT in the call chain of fetchByAccountIdList (the system uses a SQL query with voided_at IS NOT NULL filter, not fetchById). No Specimen 1 (hard-wired counts) -- the RPT-1.7 test uses F-prefixed fixture account codes as locators with small integer generations that are structural properties of the known fixture hierarchy, not counts that drift. No Specimen 2 (cowardly inequalities). No Specimen 3 (count-only) -- all tests assert values. No Specimen 4 (untyped failure) -- the ReportRoutes tests use typed DU matching (DataOnly vs Report). No Specimen 5 (exit-code-only) -- none of these tests assert only exit codes. No Specimen 6 (fox guarding hen house) -- all expected values derived from fixture data via list operations, confirmed by reading the source call chains.

Considered flagging RPT-1.9's vacuity guard (checks entries exist before cutoff but not after), but the exact-equality assertion against correctly-derived expected values IS the primary filter check. If the filter broke, the actual values (including post-cutoff amounts) would exceed the expected values (pre-cutoff only). The fixture is intentionally designed for temporal testing (entries at -3, -1, and today). The one-sided vacuity check is defense-in-depth, and its asymmetry does not make the test ineffective today.

NEGATIVE COVERAGE: No active, non-waived REQs in the Reporting spec define rejection criteria. RPT-1.12 (empty filter rejection) is stricken/withdrawn. RPT-2.5 (file I/O failure -> typed error) is waived. No missing negative tests to flag.

UNCITED BEHAVIOR: No tests exercise reporting logic not described in the spec. The Reports/Program.fs tests cite NGUI REQs (different auditor's scope). The source code (TrialBalance.fs, AccountBalance.fs) implements exactly the behaviors described by the REQs. No undocumented code paths found in the reporting source that lack REQ backing.
