# code-outward-coverage-CrossDomainOrchestration

## CDO-COV-EMPTY-1 — test-gap
- **Location:** Src/Business.CrossDomainOrchestration/InvestmentActivityOrchestration.fs:139 (recordActivity); Src/Business.CrossDomainOrchestration/PreLedgerBalanceOrchestration.fs:101 (recordPreLedgerBalances); REQ-POS-13.1, REQ-POS-15.4, REQ-SYS-6.1
- **Summary:** Both new slice 2 batch-record operations reject an empty request list (PositionsActivityRangeListIsEmpty and PositionsPreLedgerBalanceListIsEmpty), but no test sends an empty list to either. Last audit's #020 asked for exactly this test on the snapshot equivalent.
- **Resolution:** fix-test
- **Prior ruling:** Audit 2026-10-04a disposition #020 (CDO-COV-POS-7, accepted): reject an empty snapshot list with a typed error, and test-agent adds a route test. This finding applies that ruling to the two operations slice 2 added. It does not re-raise the snapshot point, which is fixed and tested.

recordActivity begins with `do! if ranges |> List.isEmpty then error PositionsActivityRangeListIsEmpty else Ok()` (InvestmentActivityOrchestration.fs:139), and recordPreLedgerBalances begins with the same guard returning PositionsPreLedgerBalanceListIsEmpty (PreLedgerBalanceOrchestration.fs:101). An operator can reach both. The routes PositionsRoutes.fs:267-280 (InvestmentActivity Record) and :305-313 (PreLedgerBalance Record) map `input.ranges` and `input.balances` straight through, so `{"ranges": []}` or `{"balances": []}` arrives at the guard. The requirements call for these guards: REQ-POS-13.1 says 'record the activity of one or more Investment Accounts in a single atomic operation', and REQ-POS-15.4 says 'record one or more Pre-ledger Balances in a single atomic operation'. A grep of git-tracked Tests/*.fs finds neither error case, and Checks/check-apperror-coverage.sh run on HEAD lists both as 'untested'. The snapshot equivalent, PositionsSnapshotListIsEmpty, does have a test (PositionsRoutes.fs:1153). That test was added under audit 2026-10-04a disposition #020 (accepted), which ruled that an empty list is a silent no-op contrary to 'one or more' and REQ-SYS-6.1 and asked test-agent for a route test. The two new operations repeat the guard without the test.

**Action:** Add two tests modelled on PositionsRoutes.fs:1153. One sends an InvestmentActivity Record payload with `ranges: []` and matches PositionsActivityRangeListIsEmpty, citing REQ-POS-13.1 and REQ-SYS-6.1. The other sends a PreLedgerBalance Record payload with `balances: []` and matches PositionsPreLedgerBalanceListIsEmpty, citing REQ-POS-15.4 and REQ-SYS-6.1.

**Why:** Dan's statement says error cases that only reject loudly are untested by design. These guards don't fit that description. If either were removed, an empty request would return Ok [] and commit nothing, with no error at all. That is the silent no-op REQ-SYS-6.1 forbids and the upstream parser failure #020 was meant to expose. A regression here produces no loud failure for anyone to notice, so a test is the only thing that would catch it.

## CDO-COV-ACT-1 — test-gap
- **Location:** Src/Business.CrossDomainOrchestration/InvestmentActivityOrchestration.fs:60 (buildActivity -> InvestmentActivity.confirmDatedInRange) and :151-155 (recordActivity -> InvestmentActivity.confirmRangesDontOverlap); REQ-POS-13.1, REQ-POS-13.2, REQ-POS-13.3
- **Summary:** The out-of-range check and the overlapping-range check are tested only as isolated domain functions. No test drives recordActivity into either rejection, so dropping either call from the orchestrator would leave every test green while activity was silently lost or double-counted.
- **Resolution:** fix-test

Tests reach PositionsActivityOutsideRange and PositionsActivityRangesOverlap only in Tests.Isolated/Model/Positions/LotsAndActivity.fs (:241 for REQ-POS-13.1 out-of-range, :268/:280 for REQ-POS-13.3 overlap), and those call InvestmentActivity.confirmDatedInRange and confirmRangesDontOverlap directly. The behaviour that matters is wired in the orchestrator: buildActivity calls confirmDatedInRange (line 60), and recordActivity calls confirmRangesDontOverlap (lines 151-155) before any range is replaced. A grep of Tests.Integrated (InvestmentActivityRecording.fs, PositionsSliceTwoRoutes.fs) finds neither error case and no test sending overlapping ranges or an activity dated outside its range through recordActivity or the InvestmentActivity Record route. Other recordActivity validators do have orchestrator-level tests: PositionsActivityRangeEndsAfterCurrentDate (InvestmentActivityRecording.fs:181, which also covers the confirmRange call), PositionsActivityDateOutsideActivePeriod, PositionsActivitySecurityNotHeld and PositionsActivityShapeInvalid (PositionsSliceTwoRoutes.fs:238). These two checks are the exceptions. Without them, recordRange (lines 103-132) does damage: it deletes the account's activity between begin and end and then inserts what was supplied. With two overlapping ranges for one account, the second range's delete removes activities the first range just inserted on the shared dates. An activity dated outside its range is inserted without the existing activity on its date being removed, so a re-supplied period is counted twice, which is the duplication REQ-POS-13.2's replacement rule exists to prevent.

**Action:** Add two integrated tests that call recordActivity, or the InvestmentActivity Record route. (a) Two ranges for one account that share one day are rejected with PositionsActivityRangesOverlap naming the account and both ranges, and the account's previously stored activities are unchanged (REQ-POS-13.3). (b) A range containing an activity dated the day after its end date is rejected with PositionsActivityOutsideRange naming the account, the range and the date, and nothing is stored on that date (REQ-POS-13.1).

**Why:** The question is whether this code path has any test, not whether the REQ does. The domain functions are tested, but the orchestrator's calls to them are what stop data loss. Removing either call does not fail loudly: the operation returns Ok with plausible removed and recorded counts, and the stored activity history, which the unit roll-forward and the Monte Carlo inputs read, becomes wrong without any sign of it.
