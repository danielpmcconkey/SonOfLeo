# ClassificationRuleCrud spec-quality auditor

## AMB-CR-5.3-SRCLEN — insufficient-elaboration
- **Location:** Specs/Behavioral/ClassificationRuleCrud.md REQ-CR-5.3 (with REQ-CR-1.19); Src/Ui.InterfaceBridge/BoundaryConverters/ClassificationFieldConverters.fs `convert [ClassificationRuleFilterInput] to [ClassificationRuleFilter]` (sourceLike arm); Src/Business.FinancialServices.Ledger/JournalEntryComponent.fs JournalRefFinancialInstitution (max = 100)
- **Summary:** REQ-CR-5.3 does not say what text the source-pattern filter accepts. The code validates it as a journal entry external reference's Financial Institution: trimmed, at most 100 characters, and refused with a ledger error. The patterns it searches can be up to 500 characters.
- **Resolution:** dan-decides

REQ-CR-5.3 offers a 'source pattern (case-sensitive partial match against the text of any `Source` field match in the rule)' filter and says nothing about length or validation. REQ-CR-1.19 allows a stored Source pattern of up to 500 characters. The converter builds the filter with `filterInput.sourceLike |> convertOptionToDesiredTypeWithFallibleConverter JournalRefFinancialInstitution.create`. That function trims, refuses anything over `max = 100`, and returns `JournalRefFinancialInstitutionTooLong`, which reads: "Journal Entry External Reference's Financial Institution cannot exceed 100 characters." So an operator who pastes a 120-character Source pattern to find the rules that use it gets a refusal about journal entry external references, a ledger concept unrelated to classification. The sibling name filter is validated against the rule's own name type (ClassificationRuleName.create, 250 characters, the same limit as REQ-CR-1.4), so the source filter is the odd one out. Two reasonable implementers would differ here: one bounds the filter by the pattern limit (500, REQ-CR-1.19), the other picks some other limit or none, and the operator sees different results. No test sends an over-length source filter (grep of Tests/ for sourceLike: every use is a short tag). Precedent: in 10-04a, item #144 (CON-CR-1.18-SYS) mentioned the 100-character cap only in passing, as an optional note. Its disposition added REQ-SYS-1.5, which settles trimming (no exemption is stated, so SYS-1.1 applies). It made no ruling on the length bound or on the borrowed type, so no ruling covers this exact point.

**Action:** Amend REQ-CR-5.3 to state the source-pattern filter's text limit. The natural choice is REQ-CR-1.19's 500 characters, since the filter is a fragment of a pattern. Then impl-agent validates the filter with a classification-domain type and error instead of JournalRefFinancialInstitution, and test-agent adds a REQ-CR-5.3 test at the boundary.

**Why:** The filter searches patterns, but its accepted input comes from an unrelated ledger type. That type's 100-character limit is a fifth of the patterns' 500, and its error message names the wrong domain. The spec's silence leaves the limit to whichever type an implementer happened to reach for.

## README-CR-FUNC-NAMES — stale-reference
- **Location:** Specs/Behavioral/ClassificationRuleCrud.md REQ-CR-2.8 *Why* line; Waived table row REQ-CR-4.2
- **Summary:** The spec names code functions (`List.forall` in REQ-CR-2.8's Why, `Guid.NewGuid()` in the REQ-CR-4.2 waiver reason). Specs/README.md forbids this: "Spec documents never name source files, functions, or tests."
- **Resolution:** fix-spec

Specs/README.md, Linkage rules: "Spec documents **never** name source files, functions, or tests." Requirement anatomy: "A requirement is written in operator concepts: it says what the system does, never how the code is structured." REQ-CR-2.8's Why reads: "`List.forall` on an empty list returns true (vacuous truth)." The REQ-CR-4.2 waiver reason reads: "UUID generation via Guid.NewGuid() in create; uniqueness enforced by PK constraint." Both name a specific library function. REQ-CR-2.9's Why borrows the same reasoning ("Same vacuous-truth hazard as REQ-CR-2.8"). Neither text is wrong today: ClassificationComponent.fs does call Guid.NewGuid(). But each ties spec text to an implementation choice that can change without any change in behaviour, which is the drift the README rule exists to prevent. No other behavioral spec has the `NewGuid` wording: the parallel waivers for REQ-AC-2.13, REQ-FP-2.1 and REQ-JE-2.1/2.2 do without it. resolved-findings.md has no ruling on function names in CR spec prose.

**Action:** Reword REQ-CR-2.8's Why to state the hazard in operator terms, for example: "'every match in an empty chain is true' holds vacuously, so without a guard an empty chain would match every candidate." Reword the REQ-CR-4.2 waiver reason to: "The ID is generated by the system on create and is not an input; uniqueness is enforced by the primary key. Same rationale as REQ-CR-1.1."

**Why:** Specs are the authority above code, and the README keeps them that way by never pointing at code. A spec that names a function is wrong as soon as the code is refactored, though behaviour has not changed, and a future auditor reading it may treat that function as part of the requirement.
