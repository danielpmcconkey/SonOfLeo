# code-truthfulness-auditor:App.Utility/App.Operation/App.Session

## SD-JSON-1 — statement-delta
- **Location:** Src/App.Utility/Json.fs:18-44 (missingFieldMessage / fromJson); affects Src/Ui.InterfaceBridge/InterfaceContracts/PositionsContracts.fs:138-147 (AccountSnapshotInput inside AccountSnapshotRecordInput), JournalContracts.fs:14-35,100 (JournalEntryHeaderInput inside JournalEntryInput; JournalEntryCommentInput inside JournalEntryVoidInput / JournalEntryAddCommentInput)
- **Summary:** Dan says Json.fromJson now names the field a payload actually left out, but the correction only applies when the missing field is in the top-level record being read; when it is in a nested record, the error still names a null option field instead.
- **Resolution:** dan-decides

Dan's statement: "App.Utility.Json.fromJson, which every route shares, now names the field a payload actually left out." The code is narrower. missingFieldMessage<'T> builds prefix = "Missing field for record type {typeof<'T>.FullName}: " and rewrites the library message only when it starts with that prefix (line 25). Its own docstring (lines 18-21) says so: "When the record the library names is the one being read ... any other message is returned as the library gave it." FSharp.SystemTextJson (1.4.36, App.Utility.fsproj:27) deserialises each nested record with that record's own converter. A missing field inside a nested record therefore raises "Missing field for record type <NestedType>: ...". That message does not match the prefix built from 'T, so it is passed through unchanged, with the defect the commit describes: a null option field declared before the omitted required field is the one named. The commit is 2387cde: "A payload that sent null for an option field and left off a required field declared after it got an error naming the option field". Live routes where this happens: (1) AccountSnapshot Record. PositionsRoutes.fs:188 reads AccountSnapshotRecordInput { snapshots: AccountSnapshotInput list }, and AccountSnapshotInput declares contributionBasis: decimal option before lines. A snapshot sending "contributionBasis": null and leaving out "lines" gets an error naming contributionBasis. (2) JournalEntry Create. JournalEntryInput.header is JournalEntryHeaderInput { description; source: string option; entryDate }. A header with "source": null and no entryDate gets an error naming source. (3) JE Void and AddComment. JournalEntryCommentInput { secondaryJournalEntryId: Guid option; commentText }, nested as reason or comment. A payload with secondaryJournalEntryId null and no commentText gets an error naming secondaryJournalEntryId. The route tests that cover the fix (PositionsRoutes.fs:432, 821, 836, for REQ-POS-4.7, 9.4 and 9.5) all leave out a top-level field, so none of them exercises the nested case. I did not run this, because dotnet is not available in the audit container. The behaviour follows from the prefix guard and from the library limitation described in the code's own comment.

**Action:** Either extend missingFieldMessage to cover nested records (parse the record type the library named, find the matching JSON object(s) in the payload and name the first field missing there), or narrow Dan's mental model and the code comment to say the correction applies only to fields of the top-level payload record. Then add a route test for one nested case (e.g. an AccountSnapshot Record payload with contributionBasis null and lines omitted).

**Why:** Snapshot payloads are produced by external parsers that Dan says live outside the repo. The error message is the only diagnostic such a caller gets. An error that names a field the payload did send (as null) sends the caller to the wrong field. That is the defect the change was made to remove, and it is still present on the nested payload shapes that the Positions slice adds.
