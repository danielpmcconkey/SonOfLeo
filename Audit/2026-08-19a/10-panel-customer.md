# Hobson (Customer Audit — NEAR/MID/FAR)

## CUST-FETCH-1 — customer-gap
- **Location:** Src/InterfaceBridge/Routes/IngestionRoutes.fs; Src/ModelOrchestrator/StageEntryOrchestration.fs lines 229-270
- **Summary:** The data-ingestion slice has no CLI route to query staged entries by status, source file, or ID, despite the orchestrator layer exposing fetchAllByFile, fetchByStageEntryHeaderId, and fetchAllForPosting.
- **Resolution:** fix-code

IngestionRoutes.fs exposes eight ingestion CLI routes: IngestRawFileToStage, NewClassificationRule, FetchClassificationRuleById, FetchClassificationRuleByName, FetchClassificationRuleFiltered, CreateIngestionSource, UpdateStageEntry, and PostStageEntries. Classification rules have three fetch routes; staged entries have zero. The orchestrator has fetchAllByFile (by source file + optional status filter, line 229), fetchByStageEntryHeaderId (by UUID, line 259), and fetchAllForPosting (Classified + Reviewed, line 242), but none are wired to a CLI route. The IngestRawFileToStage route returns staged entries as part of its IngestionFullResultReturn, but this is the only way to see staged entry data through the CLI — and only for the file just ingested, in the same session. The Saturday routine Phase 2 requires surfacing all NoMatch/Conflict entries across multiple imported files (the LeoBloom equivalent was a UNION ALL across stage tables, filtered by status). The UpdateStageEntry route requires a stageEntryHeaderId (UUID) and line IDs (UUIDs) that the operator can only obtain from the initial IngestRawFileToStage response; if that response is lost (session ends, output not captured), the operator has no CLI path to rediscover those IDs. The shadow post (PostStageEntries with isShadow: true) shows trial balance before/after but not which entries are in the batch — and without a fetch route for postable entries, the operator cannot correlate the trial balance delta with specific staged entries. This forces the review workflow — which the spec explicitly describes in section 6 (Manual review behaviors) — back to raw SQL, which is the exact pattern the ingestion domain was built to replace.

**Action:** Expose at least two staged entry fetch routes: (1) fetch by status (accepts a list of statuses, returns StageEntryReturn list) for the Phase 2 review surface, and (2) fetch by header ID (accepts a UUID, returns a single StageEntryReturn) for targeted inspection before UpdateStageEntry. fetchAllByFile with status filter would also serve file-scoped review. The orchestrator already implements all three; this is a routing-layer gap only.

**Why:** The ingestion domain's value proposition is that import operations — including review and classification — happen through the CLI, not through raw SQL. A domain that can ingest, update, and post staged entries but cannot query them delivers two-thirds of its intended workflow. The missing third is the one the customer (the comptroller agent) spends the most Saturday time on: reviewing what the classifier couldn't handle.

## CON-POSTABLE-1 — contradiction
- **Location:** Specs/Definitions.md (Postable definition) vs Specs/Behavioral/DataIngestion.md REQ-STG-4.4
- **Summary:** Definitions.md defines Postable as requiring both status (Classified/Reviewed) AND all lines having non-null account_code, but REQ-STG-4.4 explicitly states that no line-level account_code filtering is applied — the postability check is status-only.
- **Resolution:** fix-spec

Definitions.md says: 'A staged entry whose status is Classified or Reviewed and whose every staged line has a non-null account_code. Only postable entries are eligible for shadow post or batch post.' REQ-STG-4.4 says: 'A staged entry is postable when its status is Classified or Reviewed. No additional filtering (e.g. line-level account_code presence) is applied — if the upstream invariants are sound, all lines are coded by the time an entry reaches these statuses.' The spec explicitly names 'line-level account_code presence' as an example of filtering that is NOT applied, while the definition includes it as a condition. The code follows the spec: fetchAllForPosting (StageEntryOrchestration.fs line 242) fetches by status only, then confirmLinesAccountCodes with DisallowNone (line 584) validates before posting. The Definition is authority level 2; the spec is authority level 3. The spec explicitly chose to diverge from the definition's condition. The operational consequence: if an operator transitions a NoMatch entry to Reviewed without assigning all account codes — which the system permits (updateStageEntry uses AllowNone at line 520) — the entry is included in the postable set (status = Reviewed), fails pre-post validation, and rolls back the entire batch (REQ-STG-9.8). Under the Definition's semantics, the entry would be excluded from the postable set, and other good entries would post successfully.

**Action:** Update the Postable definition in Definitions.md to match REQ-STG-4.4's intent: remove the 'and whose every staged line has a non-null account_code' clause. The definition should describe what the system actually does (status-only postability check with loud failure at posting if upstream invariants are broken), not a stricter condition the spec explicitly rejected.

**Why:** The authority hierarchy says Definitions.md (level 2) outranks behavioral specs (level 3). When the two disagree, an auditor, a test writer, or the operator (this customer) cannot know which to trust. The spec's Why note makes the design intent clear (fail loudly rather than silently exclude), but the Definition contradicts it. Keeping both documents in sync is what makes the authority hierarchy useful rather than a source of confusion.
