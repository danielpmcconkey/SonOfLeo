# Solution Conventions

Code and naming conventions for the SonOfLeo solution. These are developer-facing rules
enforced by review, not behavioral requirements verified by tests — that's why they live
here and not in a Behavioral spec with REQ- IDs.

## Naming

- **Smart constructor naming — `create` vs `fromString`:** does the type *wrap* the input?
  Use `create` (e.g., `AccountName.create`, `AccountActivityPeriod.create`). Does the input
  merely *name* one of a fixed set of cases? Use `fromString` (e.g., `AccountType.fromString`,
  `AccountSubtype.fromString` — parse boundaries from a string label to a DU case).
  `create` is the only verb that scales to multi-arg constructors; `fromString` is the honest
  name for parsing an enumeration's label. Don't unify them.

## Requirement traceability

- **Code annotations:** the implementing site of a requirement carries its ID in a comment
  (`// REQ-AC-1.5`). Annotate where the rule is *enforced*, not everywhere it is merely
  relevant.
- **Test naming:** every test name begins with the requirement ID(s) it verifies, followed
  by prose: ``let ``REQ-AC-1.7 name rejects whitespace-only`` () = ...``. Multiple IDs are
  space-separated before the prose. This is what makes the requirement→test map greppable;
  a test that verifies no requirement should make you ask why it exists.
- **Spec documents never name code or test artifacts.** Linkage flows one direction:
  destination → ID. The maps are generated by `Audit/audit.sh`.

## Build & environment

- **Building in the BD container:** always `dotnet build --artifacts-path /tmp/sonofleo-build`.
  A bare `dotnet build` writes container paths into `obj/` on the bind mount and breaks
  Rider on the host.
